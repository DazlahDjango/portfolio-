How to use this catalogue
This guide is a pricing and portfolio-planning reference for a developer or small software studio. It starts with Flask, then covers Django and other backend choices, frontend applications, databases, standalone Python tools, AI/automation, infrastructure and full-stack combinations. The catalogue also includes supporting dependencies and 40 CSS colour palettes.
Prices are suggested starting estimates, not fixed market quotations. They assume a legitimate, original implementation and vary with requirements, delivery deadlines, integrations, security, data migration, hosting, user volume, support commitments and local taxes.
Pricing labels
One-time build / purchase: indicative fee to design, build and hand over a project at the stated scope. It is not a price for buying a third-party framework.
Monthly licence: an optional recurring fee for a hosted product, subscription access, updates or support. It is not automatically required for open-source software.
Annual licence: the suggested yearly subscription amount, typically discounted compared with paying month by month.
Currency order throughout: USD | Kenyan shillings (KES) | euros (EUR). Converted values use the reference rates on the cover and are rounded for readability.
Open-source frameworks and libraries may be used without a software licence fee under their respective licences; hosting, support, development and managed services can still cost money.
Quick pricing principles
Small landing pages and utilities: keep the scope narrow and define the number of pages, forms and revisions.
Business systems: price discovery, role-based access, audit trails, reporting, imports/exports and integrations separately where appropriate.
SaaS / multi-tenant platforms: include tenant isolation, billing, monitoring, backups, disaster recovery, support and security testing in the estimate.
Use milestones: discovery and specification, UI/design, core implementation, testing, deployment, handover and post-launch support.
Write down what is excluded: cloud hosting, paid APIs, SMS/email usage, payment-provider charges, third-party subscriptions and future feature changes.

Part 3 — Dependencies and supporting services
Dependencies are selected according to the actual architecture. Avoid installing every package in a catalogue: choose only what the application needs, pin compatible versions, scan dependencies and keep a lock/requirements file.
Flask / Python backend
Flask; Werkzeug; Jinja2; Flask-SQLAlchemy or SQLAlchemy; Flask-Migrate/Alembic; Flask-Login or a token library; Flask-WTF where forms/CSRF are used; Marshmallow or Pydantic; pytest; Ruff; Gunicorn or Waitress; python-dotenv for local development.
Django / REST APIs
Django; Django REST Framework; SimpleJWT or another chosen auth mechanism; django-filter; drf-spectacular; django-cors-headers only when required; django-environ; psycopg; django-redis; Celery; django-celery-beat when scheduled tasks are needed; pytest-django; Ruff; Gunicorn or Daphne/Uvicorn depending on ASGI/WSGI needs.
Frontend
React/Vue/Angular/Svelte as selected; TypeScript; Vite or framework-native tooling; React Router or equivalent; TanStack Query or equivalent data-fetching library; Zod or another schema validator; accessible component primitives; ESLint; Prettier; Vitest/Jest; Playwright/Cypress; an approved icon library.
Databases and storage
PostgreSQL or MySQL/MariaDB; psycopg or matching driver; Redis for cache/queues where needed; object storage for user uploads and backups; migration tooling; connection pooling where justified; backup verification and restore drills.
Background tasks and messaging
Celery with Redis/RabbitMQ where appropriate; task retry/idempotency rules; dead-letter/retry monitoring where supported; email provider SDK; SMS provider SDK only when required; webhook verification; scheduled jobs via Celery Beat or a controlled scheduler.
Production and operations
Docker; Docker Compose for local/multi-service development; Nginx or a managed reverse proxy; TLS certificates; environment/secret management; CI/CD; structured logs; error tracking; uptime checks; metrics and alerting; backup encryption; disaster recovery runbook; firewall and SSH hardening.
Suggested baseline for a Django SaaS
Area	Suggested baseline
Application	Django + Django REST Framework; split settings by environment; clear apps and service boundaries.
Data	PostgreSQL with migrations, constraints and tested backups; use tenant-scoped query controls and database-level protections where appropriate.
Cache and jobs	Redis for caching/queues; Celery workers for email, reports and long-running tasks; define retries and idempotency.
Frontend	React + TypeScript + Vite or another intentionally selected framework; validate API contracts and manage auth carefully.
Security	MFA where appropriate, secure cookies/tokens, least privilege, audit logs, rate limiting, CSRF/CORS configuration, secrets management and dependency updates.
Deployment	Docker images, reverse proxy, TLS, health checks, monitoring, logs, scheduled backups and tested restore/disaster recovery procedures.
Scale	Add load balancing, connection pooling, object storage, worker scaling and orchestration such as Kubernetes only when operational needs justify the added complexity.

Part 5 — Licensing, ownership and commercial terms
Topic	What to define in the proposal or contract
Open-source dependencies	Read the licence of each dependency and any transitive dependency. MIT, BSD and Apache-2.0 commonly allow commercial use subject to their conditions; copyleft licences may impose additional obligations. This is general information, not legal advice.
Client ownership	Specify whether the client receives source code, deployment scripts, design assets, documentation and intellectual-property rights. Define any third-party or reusable components that remain the developer's property.
Hosted software licence	A recurring licence should define the number of users/tenants, usage limits, storage, availability target, support hours, update policy, cancellation, data export and data deletion.
Maintenance and support	Define response times separately from resolution times. State whether support covers defects, hosting incidents, minor changes, security updates or new features.
Third-party charges	List cloud hosting, domains, email/SMS, payment processing, maps, AI/API usage and app-store fees as separate pass-through charges unless explicitly included.
Security and privacy	Set responsibilities for access controls, personal-data handling, retention, backups, incident response and compliance with applicable laws and contracts.
Acceptance and changes	Use written acceptance criteria, a limited defect warranty period, and a change-request process for work outside the agreed scope.
